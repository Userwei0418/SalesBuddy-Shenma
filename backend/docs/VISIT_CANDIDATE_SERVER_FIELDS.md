# 拜访候选的后端字段边界

拜访正文与质量审核由 AI 整理，客户主档和记录人由后端提供。`visit_entry` 的事实加载器在当前身份的只读事务中生成 `server_fields`，平台与直调共用同一结果契约。

| 候选字段 | 来源与规则 |
| --- | --- |
| `customer_name` | 已绑定客户时，使用与归档相同的 `security.customer_reference`；未绑定时保留原文名称作为待匹配候选。 |
| `customer_type` | 已绑定客户的数据库 `customer_type_code`；未绑定或主档未填写时为空，不根据商机、金额或文本推断。 |
| `created_date` | 数据库当前日期，按上海时区生成录入日期默认值。现有确认页仍可修改，归档对应 `recorded_on`。它不是数据库不可修改的真实创建时间 `created_at`。 |
| `recorder_user_id` | 沿用现有表单键，显示当前账号在数据库中的姓名；正式归档的人员主键仍从认证身份读取。 |

事实中只加入这四个字段，不读取客户联系人、电话、历史拜访或经营汇总。FDE 仍须在加载事实与写入结果前通过现有商机参与资格和权限版本校验；使用公司客户参考不扩大客户详情权限。

`server_fields` 只能由事实加载器传入结果验证函数。它有固定字段白名单，不接受自由字段映射；模型在顶层伪造同名对象会被丢弃，模型返回的主档字段会被可信值覆盖。模型原始输入对象不被原地修改，已保留的审计证据不会因此重写。未绑定时仍允许模型从原文提取客户名称用于匹配。

这一步不改变沟通内容、下一步计划、首次拜访字段或分数；“拜访审核 v2”仍必须逐字保留受审正文。平台输出、平台失败后的直调兜底，以及关闭平台后的原直调都执行同一拜访结果契约。历史候选与历史归档不批量重写；正式归档仍按提交时的主档和认证身份校验。

验证覆盖：错误客户类型和录入日期被可信默认值纠正；伪造同名字段不能覆盖；未绑定客户不猜类型；平台/兜底/原直调一致；重审正文不变；真实 PostgreSQL 客户参考在当前身份下可读且不扩散联系人信息。

2026-09-13 验证结果：拜访平台、表单、评分政策和演示 runner 相关离线测试 **77 passed**；FDE 个人页回归 **14 passed**。真实 PostgreSQL 验证 **16 passed**（既有平台/归档 14 项，加候选客户参考与无绑定默认值 2 项），使用随机临时库及不绕过 RLS 的应用角色，结束后回读确认该库与角色均不存在；测试源码和独立虚拟环境也已清理。业务演示库、线上服务和既有归档未在此验证中修改。部署与线上真实模型调用另行验收，以上不代表已经发布。
