## 实现与业务边界

- today_tasks 独立绑定、专用 ID/API Key、工作空间/用户试点及到期时间；未授权、关闭、缺少专用凭据时继续原 API，不借用其他 Agent 凭据。
- 后端先按真实身份查询 facts，再交给 Agent。超时、无效对象/格式或受控阻断走原 API，同运行只持久化一次。平台不持有数据库工具或写入凭据。
- ordered_items 只接受当前 facts 中的 source_type/source_id，拒绝重复来源、非法优先级、非文本标题/时间/原因；额外负责人、任务状态、客户/商机等字段被移除。原 API 单独模式也执行相同的输出校验。
- 本次不修改默认 facts 来源窗口、task materialize 规则、创建任务页面、API、数据库结构或已有状态机。增加可选的后端联调范围，只在原权限查询内缩小可新增任务的拜访来源；默认不生效。已有管理任务只参与卡片排序，模型不能修改其内容、负责人、优先级、截止时间、接受/拒绝/完成状态。
- 双侧均失败时不生成任务或成功卡片；受控故障留有明确标记，生产配置不继承测试故障开关。

## 用户已确认的业务规则

现有后端会自动把本人近 90 天、已确认/归档、next_action 非空且没有关联非删除任务的拜访生成本人 pending_execution 跟进任务。每客户选择一条最新的符合条件拜访，最多 30 条。即使模型未在 ordered_items 中列出候选，后端仍为所有 facts.follow_up_candidates 生成任务。任务描述/客户/商机/来源取后端事实，责任人固定本人，按来源唯一约束防重复；物化函数不直接创建 notification，但既有 12 小时到期监控可能随后新增本人的站内提醒。已有管理任务不受此生成流程修改。

中台旧草稿曾写“待确认建议”，与后端自动生成存在差异。用户此次已确认沿用后端自动生成规则；草稿已通过 CLI 最小 prompt 补丁对齐，dry-run、configure、get 回读一致，当时仍 published=false；后续授权发布结果见当前状态。没有明确时间时 Agent 返回 null，后端沿用 future_due；无效、过去日期同样走既有未来默认值。原 API 提示词和后端物化行为保持不变。

Agent 只负责规划建议，实际保存、来源/ID/负责人校验和去重由后端执行。本模式不增加人工确认；这不改变管理层创建任务的发送提醒、接受、拒绝及执行流程。原任务页面和前端入口不变。

## 演示来源限定与只读预演

新增操作配置 `AGENT_TODAY_TASKS_ACCEPTANCE_TARGET`（工作空间 UUID:用户 UUID）与 `AGENT_TODAY_TASKS_ACCEPTANCE_PATH`（非秘密范围 JSON）。两项都为空时保留原业务行为。指定目标后，其他用户在读文件前就跳过，因此该测试文件缺失、过期不会影响他们的待办；目标配置本身必须合法。此配置不决定使用中台还是原 API，normal/off/blocked/production 都受同一来源限制。

范围文件按工作空间及用户映射，记录 approval_status、有效期和最多 30 条来源 ID/正文指纹。只有明确 approved 且未过期的范围可用于测试；缺失、损坏、过期或目标条目被删除时失败封闭，不能自动恢复全量查询。操作方可以明确写入 approved + enabled=false 结束测试限制；已经按旧范围开始的运行仍会在落库前因范围变化被拒绝。

候选查询在原 RLS、本人、归档状态、90 天、未生成任务条件内增加来源 ID 过滤，再按客户选择最新符合条件记录。每条返回候选还需通过演示标记与内容指纹检查。落库事务重新核对配置并锁定选中拜访及客户，验证来源没有被改写、删除或转移。权限配置和指纹不进入模型输入；本人已有活跃任务仍按现有查询参与展示排序，不代表可修改其正式字段。
