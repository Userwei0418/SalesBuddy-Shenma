# 商机更新群通知

用户于 2026-09-27 确认：商机更新也推送。原有新增客户、新增商机、归档跟进通知保留；更新通知独立成卡，不改写已发送卡片。

## 业务行为

- 小程序独立商机编辑、后台商机编辑、拜访归档时确认商机修改，都通过同一个保存服务生成变更记录。仅真实变化时通知，包括金额、阶段、名称、预计关单、渠道/伙伴、产品线、跟进计划、季度预测和协助 FDE。
- 卡片展示商机、客户、修改时的负责人、修改人、北京时间和修改前后值。金额明确显示元及万元/亿元量级；例如将 10 亿元纠正为 10 万元，会显示 `1,000,000,000元（10亿元） → 100,000元（10万元）`。
- 沿用各公司的现有通知群和部门路由。部门取变更发生时的部门；已规划的群和内容在重试时保持不变。
- 无变化的保存、AI 后台更新、只更新时间戳、历史初始化和历史导入不发更新卡片。已导入商机之后由人员正常编辑，则可以通知。
- 同一次变更在同一群只生成一份投递记录。明确失败使用原卡片和去重标识重试；发送结果未知时保留待核对状态，不盲目重发。不同变更分别推送。
- 开关关闭期间不补积压通知；旧版事件和既有变更记录不追发。该规则针对商机更新，原新增事件策略不变。

后台“飞书同步”增加“商机更新通知”开关，配置字段为 `notification.on_update`，默认 `['opportunity']`、关闭为 `[]`。总开关仍为 `notification.enabled`。旧配置未填写新字段时使用默认值；只有同步、总通知和商机映射原本均开启的公司，配套发布后才会通知新发生的人工更新。保存配置仍会暂停同步，须校验后再启用。

## 数据与接口

V188 为 `ops.feishu_event` 增加可空 `notification_snapshot`。`crm.business_change` 的新人工商机更新在同一事务内追加通知事件，事件 ID 取业务变更 ID；事务失败则两者一起回滚。旧同步事件保持 NULL，原表格同步触发器不改。

快照仅保存通知所需的身份、名称、时间、币种及 `label/before/after` 标量差异。DB 校验同公司关系、请求身份、生产数据和模块/通知资格，且快照不能被 Worker 后续替换或补填。服务再次核对快照公司/商机身份，不从当前可变业务行猜测旧值。同步和通知资格独立；即使 Base 已是最新值，仍处理本次冻结的通知。

新增通知的原去重标识保持不变；更新标识附加业务变更 ID，既防重试重复，又允许同一商机后续更新正常推送。现有通知总开关及更新类型撤权后，未发送的冻结卡片会结束投递，保留已发送及结果未知的回执。

商机现有编辑入口禁止更换负责人；本需求不新增商机转交能力。客户认领、团队目录调整等不等同于人工确认的商机更新。今后新增正式商机写入口须沿用变更记录，不依赖直接 SQL UPDATE 自动发群卡片。

OpenAPI 已新增通知配置字段。业务保存 API 没有新增请求字段；此项不需要小程序 UI 或重新上传小程序。金额确认等同批功能的前后端配套要求仍需遵守。

## 发布与验证边界

V188、API/后台静态资源和飞书 Worker 要一起发布，切换时停止旧消费者，避免旧 Worker 将新通知事件当普通同步事件消费。迁移不修改公司配置、不回填历史、不发送消息。回退前须核对未完成队列和发送结果，不能盲目重放业务变更。

本轮仅本地和隔离数据库验证，飞书客户端为替身，未向真实群发送。真实群可见性和实际延迟需在后续受控发布验收时核对。相关测试为 `test_feishu_sync_policy.py`、`test_feishu_cards.py`、`test_feishu_update_service.py`、`test_feishu_console.cjs` 和 `integration/test_feishu_opportunity_updates.py`。
