# 飞书单向同步运行说明

系统数据库是唯一事实来源。飞书修改不会反写，下一次核对会以系统值覆盖。原 CRM-V3 保持只读，所有写入只针对配置中的新 Base。

2026-09-27 本地候选版新增商机更新通知，规则与配套发布见 [商机更新群通知](OPPORTUNITY_UPDATES_20260927.md)。下文上线顺序保留首次 V105 接入步骤；“仅新增、修改静默”是旧版本范围，不适用于配套 V188 的人工商机更新。新能力尚未部署，不能把本地测试视作线上群消息验收。

## 小程序与运营后台发布边界

飞书同步沿用小程序现有客户/商机/正式跟进 API，触发与发送均在后端。本轮未改小程序源码，无需替换体验版。运营后台配置页随后端部署；修改公司配置后仍须保存、校验、启用。当前运行版本和真实通知验收见 [上线与通知验收交接](RELEASE_ACCEPTANCE_20260919.md)。

群历史读取权限仅用于自动化回读，不是同步或发卡片的必要权限。若回读接口因额外群消息权限拒绝，可在获授权的群页面核对卡片；不要为验证发消息默认扩大读取范围。

## 上线顺序

1. 通过数据库负责人对 V105 的审核，备份后按 `deploy-forward-release.sh` 部署；旧迁移不修改。首次部署时不存在启用连接，因此不会产生飞书写入。
2. 创建独立 LOGIN 数据库角色，设置 NOSUPERUSER、NOBYPASSRLS、NOCREATEDB、NOCREATEROLE，只加入 `salegent_feishu_worker`。不得复用业务应用角色；不得额外授予业务表或管理函数写权限。
3. 通过运维安全渠道配置 `/etc/sales-feishu-sync.env`，仅包含 `FEISHU_SYNC_DATABASE_URL`。文件 root:root 0600，不入仓库、不显示到终端。使用现有 `/etc/sales-runtime-credentials.env` 引用相同加密 keyring，不复制密钥到聊天或交付包。
4. 安装 `backend/deploy/sales-feishu-worker.service` 并启用。此服务是 `sales-worker.service` 的依赖，随原 Worker 停止/启动，避免发布切换时旧进程继续运行。启动自检要求专用角色，无业务写权限及白名单外 SECURITY DEFINER 执行权限。
5. 运营后台选择目标公司，进入“飞书同步”。导入对应目标的配置模板；核对 App ID、Base、十张表及字段映射、通知群。由管理员在密码框填写 App Secret，保存后仅加密落库，页面不回显。
6. 保持通知关闭，点击“检查连接与字段”，通过后启用同步、执行“同步历史数据（不通知）”。核对十类对象及关联，验证修改、删除/撤回、恢复和公司隔离。
7. 真实写入验收后再配置通知，重新保存、校验、启用。原通知覆盖客户、商机、正式跟进新增；V188 配套版另外支持人工商机更新的独立开关。历史初始化、周期核对不通知。验收卡片先使用获授权的测试群，部门路由由公司配置控制。

## 状态与恢复

- 保存配置会暂停，修改后必须重新校验。暂停不能撤回已发出的网络请求，需等在途任务结束再迁移或处理失败。
- 常规失败按退避自动重试，达到次数上限进入“需要处理”。先解决字段、权限或网络原因，再暂停并用“重新排队”；须填写处理说明。
- 通知超时会记为“结果待核对”，不自动重发。到目标群核对后选择“已在群中看到”或“结束此通知，不再发送”，随后可重新排队继续数据同步。两者均不会重新发送该通知。
- 崩溃留下的 running 租约由启用状态的 Worker 在到期后接管。若连接已暂停且有遗留 running，先确认旧进程结束，再恢复 Worker/连接让租约恢复，处理完成后暂停。不得直接删除队列或修改通知回执。
- 调整部门群路由只影响新通知。已经规划的群和消息内容冻结，避免重试改发另一个群。
- 目标迁移必须暂停且没有 running/unknown。更换应用须填写新 Secret。旧远端记录保留，旧 pending/failed/dead_letter 全部标为 TARGET_MIGRATED，不允许再重试；新目标历史重建不补通知。
- 当前角色 ACL 迁移会保留迁移前既有业务应用角色的有效执行权限。未来新建应用角色必须显式配置函数授权，不依赖 PUBLIC；专用同步角色不能继承业务角色。

## 凭证与验收证据

不得把 Secret、数据库口令、keyring、Token、服务环境文件、业务数据导出纳入版本库。验收证据只记录版本、表和字段标识、数量、状态、脱敏错误及操作结果。API 成功、单测通过、浏览器模拟保存都不能替代真实飞书写入与群卡片验收。

## 实时与巡检的调度（V107起）

队列来源与通知资格分开：关闭新增通知仍应优先同步实时业务变化；历史导入客户后续修改也优先。定时全量巡检、手工历史初始化和明确历史导入进入后台队列。每11次领取给最早事件一次FIFO机会，不保证跨对象卡片绝对先后。V107之前的运行版本尚无此调度。
