- 我方路由默认给中台 12 秒；未完成则取消本地调用，封闭该次结果接收，并在已获得 task_id 且尚无最终结果时尝试 `/stop`，随后走原 API。stop 回执在本次被记录为 unconfirmed；用户提供的平台侧反馈称收到了 stop，两者不矛盾：请求到达不等于我方在短清理时限内收到确认。

## 我方可改进的供数

`services/agent_run/facts.py` 当前只取最近 180 天最多 12 条已确认/归档拜访；已有风险查询则取本人全部未关闭风险，没有数量上限。因此本次不是发送全部拜访历史，但风险部分会随积累增长。

`overlay_risk_attributes` 保留原 attributes，同时把兼容字段展开到顶层。本附件 24 条风险都将 suggested_action 和 agent_key 重复携带；还有 source_run_id、source_code 和空 import_meta 等运行/导入信息。这些原本供后端持久化与兼容使用，当前整体 facts 直接进入平台模型输入。

离线试算：保留全部 12 条拜访、24 条风险及顶层业务描述、建议等字段，仅从模型投影排除 `attributes/import_meta/source_code/agent_key/source_run_id`，输入由 40,999 降至 28,875 字节，减少 29.6%。该结果只是大小估算，尚未实现或验证模型质量，不能视为优化已上线。[统计证据](evidence/personal-risk-business-20260912/feedback-payload-audit.json)

建议使用专用模型字段投影，保留权限、事实、来源 ID 与后端持久化所需的原始数据。不要为减小输入直接裁掉正文，亦不要仅因 18 条旧风险不属于本次 12 条拜访就删除：已有风险承担历史背景/去重作用，改变纳入范围须单独验证业务语义。

## 60 秒建议的适用范围

当前 `AGENT_INFERENCE_PLATFORM_SECONDS` 默认 12，`AGENT_INFERENCE_TOTAL_SECONDS` 默认 45。路由实际采用平台预算与剩余总预算的较小值；只把平台设为 60，仍会先耗尽约 45 秒总预算，无法给原 API 保留足够时间。该配置目前共享多个 Agent，不能通过一个全局改动使所有线上功能都延长等待。

建议先在隔离诊断中对比“原输入/去重输入 × 12 秒/更长预算”，不写正式风险，分别记录响应头、首字、结束、解析、业务校验、取消与 stop 状态。60 秒可作诊断上限；实际试验需协调客户端、外层总预算和兜底余量。采集必要的合成/脱敏流事件，正式业务日志继续避免保存原文、完整回答或凭据。

根据实际业务合格结果及总耗时，再决定本 Agent 的供数投影、按能力配置的等待预算或分批方案。生产暂时保留原 12 秒和自动兜底；本次反馈不构成已实施的 60 秒上线要求，也不撤销已验收的原 API 兜底能力。
