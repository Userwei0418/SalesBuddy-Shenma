# 业务日期与待办来源契约

业务按北京时间展示和解释日历日期。统一入口是 `domain/business_time.py`：转换带时区时间戳时保持同一真实时刻，派生 `visit_date` 用于避免 UTC 午夜之前落在前一天。没有时区的历史输入不在指纹中擅自推测时区。真正的数据库 `created_at` 与可编辑录入日期 `created_date` / `recorded_on` 保持不同语义。

## 今日待办的期限

`domain/follow_up_schedule.py` 是平台、原 API 及兜底共同执行的日期契约。模型可以排序、说明理由，不能把来源中的截止时间替换为生成当天或明天。

- 明确期限：保留来源中的日期或时刻，包括已经过去的期限；日期不含时分时，在该来源日期使用已有公司配置的执行时刻。模型遗漏日期仍由后端使用来源；模型另给冲突日期则输出契约失败。
- 确实未写期限：沿用 `TaskSchedulePolicy` 的默认未来时间，不把默认时间说成客户承诺。
- 相对时间、无法确定归属、同一执行人有多个不同期限、非法日期或不支持的表达：整批在调用模型前失败，提示确认日期后重新生成。Worker 将业务运行记为失败、队列任务置为不可重试终态；不付费让模型猜时间，也不生成部分待办。

例如“下周一提供方案”目前需要确认成具体日期；“2099年9月15日10:00前提供方案”保留该时刻。本人行动与客户、其他同事行动分句且归属明确时，仅取本人的期限。已经存在的任务仍保留数据库中的内容、期限、优先级和状态。

已有任务的输出契约仅保留 `source_type`、`source_id` 和可选排序理由；模型多写的日期、标题、优先级、状态、负责人不会参与校验、写入或卡片展示。最终卡片在同一业务事务内重新查询数据库。新候选与已有任务按后端两个事实集合的来源键区分，不能只看 `visit_follow_up` 类型；两个集合重叠即拒绝。新候选仍需通过优先级和来源期限校验，已有任务的越权引用、重复引用或不合法解释格式仍会失败。这避免了模型复述几十条旧任务字段出错而阻断合法新候选，业务事实仍完全由数据库提供。

以上取代早期接入记录中“过去或无效日期一律补未来时间”的实现说明。早期运行结果仍是历史证据，不作为当前期限规则。

## 写入前的来源复核

`services/agent_run/today_scope.py` 的 `recheck_follow_up_sources` 同时用于普通生成与限定演示来源的生成。写入前重新读取候选对应的拜访并锁定拜访、客户行，要求同工作空间、本人记录、状态为 `confirmed` / `archived`、未删除、仍在既有来源窗口内，并与本次推理前的事实指纹一致。来源变化、不可见、缺失或重复时整批拒绝写入；不把模型成功误当成业务成功。

来源指纹覆盖来源主键/类型、客户/商机、客户名称、沟通内容、下一步计划及拜访时间。带时区时间先规范成 UTC；同一瞬间的 UTC 与 `+08:00` 表示相同，真实时间和业务文本改变仍会导致指纹改变。旧 PostgreSQL UTC 时间产生的有效指纹保持兼容。联调范围配置另做有效期与名单检查，仅可缩小业务权限，不承担普通业务的权限校验职责。

## 数据库配套与验证

V076 保留原手动任务的未来时间约束，仅让有明确拜访来源的 `visit_follow_up` 保存历史期限，并以同工作空间复合外键保护来源关系。归档状态和本人资格在上述统一写入边界核对，数据库不重复实现权限或时间文本解析，不按供应方名称特判。迁移不改历史日期，不新建表或触发器。

本轮含已有任务投影修订的全量非 PostgreSQL 测试 **1050 passed**；真实 PostgreSQL 集成 **241 passed**，岗位并发领取专项通过。新增真实验证涵盖：过去源期限原样入库；手动过去期限仍拒绝；无来源跟进和跨空间来源拒绝；相对期限产生明确不可重试失败且零模型调用、零新任务；别人的相对期限不泄漏也不阻塞本人有效来源；普通生成期间来源修改拒绝写入；平台日期冲突后由原 API 合格输出兜底；已存在管理任务及重复请求不被改变；平台、关闭平台和兜底均允许模型错误复述已有任务字段但忽略它们，合法新候选照常生成，卡片与任务原值一致，已有拜访跟进任务也使用同一只读边界。

上述 PostgreSQL 测试在独立随机技术库运行，使用不绕过 RLS 的运行角色，结束后库、角色和测试源码目录均已清理。这里记录该源码快照的验证，不代表线上已发布或真实模型语义全部正确；后续额外入口的改动与最终发布 SHA 由对应 CI、发布及业务验收记录单独证明。
