## 统计规则

|项目|本次规则|
|---|---|
|排除范围|公共销售团队 ACV/跟进榜按后端 `platform.team.attributes.kind=fde` 排除，重新计算名次。名称改变不影响规则。`sales`、`product_sales`、`general` 保留。|
|组织及事实|普通团队目录不删除 FDE团队；选择该团队仍可看原经营事实。活跃商机数事实及原 FDE 专属业务看板不改。|
|ACV|预计关单日在所选季度的在推商机金额排序，Won/Lost 不计。商机条数仅作辅助说明，没有新增或保留一个按总条数排序的团队卡片。|
|跟进周期|沿用北京时间近 7 天含今天，confirmed/archived，非软删除记录；不随金额季度筛选改变。|
|人均分母|当前启用账号在有效团队的有效 sales/supervisor/manager 业务任职，且有效 role_binding 与任职岗位匹配。按团队和人去重，零跟进也计入，纯运营/后台管理员不计入。兼后台或 FDE 不会消除另一份有效销售任职。|
|分子及归属|当前有效销售业务账号的正式跟进按 recorder_team_id 统计；旧记录没有保存团队时沿用其当前主团队兜底。转组不把已保存团队的记录搬到新团队；当前已停用或失去全部销售业务任职的账号，沿用旧榜规则不参与。|
|兼职与转组|每个团队分母分别计入有效兼职成员；单条跟进只归属一个记录团队。仍有销售业务任职、但已不在原团队的贡献者在原团队明细标注“不计入当前人数”，次数仍计入原团队，保持分子和明细一致。|
|空团队|分母 0 时 value/average/rank=null，显示无有效业务成员，不参与人均名次；可展开查看剩余原团队贡献。|
|排序与显示|按未舍入的人均数降序，完全相同时并列（1、1、3）；界面最多两位小数。不能按展示舍入值重新排名。|
|权限|团队、人员和记录分别检查 dashboard.ranking 的数据范围，限定当前租户。后台额外授权不自动改变业绩身份；返回个人聚合不授予客户、商机或跟进内容访问权限。|

## 接口与迁移

`GET /api/v1/dashboard/rankings` 保持 contract_version=2 外层和既有键，补充团队跟进契约：

- `followup.calculation=team_followup_per_capita_v1`；`denominator=current_active_sales_appointments_including_zero`。
- 每行 `value` 为未舍入人均，`average` 为两位数值，`record_count` 为总次数，`member_count` 为分母，`customer_count` 为去重客户数。
- `members[]` 含 user_id/name/account_code/current_member/followup_count/customer_count，不返回客户 ID、业务原文、邮箱或手机号。团队总数、人数和个人明细同一 SQL 语句生成；不发第二个明细请求。
- 个人跟进榜仍按次数。旧区域分组请求同样使用人均统计；实际团队请求保留真实团队 ID。
- 所选团队只影响摘要，高亮与完整榜使用同一名次。FDE团队仍保留 selection 回显，不伪造其他团队为已选。

V148 新建 `security.dashboard_team_ranking`，新增函数的 owner、EXECUTE ACL 和 grant option 精确继承既有 `dashboard_subject_ranking`，先清除部署角色的默认授权。后者原签名原 owner/ACL 保留，只去掉 FDE 团队事件和团队 roster。原 `business_ranking` 未改，活跃商机事实保持原边界。

前端需要本次后端和 V148 配套。若旧后端没有人均契约，前端明确提示配套版本尚未提供，不能把旧总次数标为“人均”。上线前需复核真实组织的 FDE 团队 kind；不得临时用名字硬编码代替。数据库负责人审核后才可进入生产迁移。灰度/回滚必须成对处理前端、后端及函数契约。
