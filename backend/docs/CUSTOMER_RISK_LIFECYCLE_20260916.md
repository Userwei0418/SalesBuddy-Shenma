# 客户风险评估后端修复与验收

本轮仅修改后端和数据库，兼容已上线小程序。现有 API 路径、请求参数和响应字段不变，不需要重新上传或提审微信包。`frontend/` 无差异；部署时只打包 `backend/` 和 `database/`。

## 行为与责任

有效归档、跟进辅助信息补充、客户资料变更、商机创建/修改、运营批准认领或核定历史归属后，在原业务事务内新增客户级异步任务。事务回滚则不留下任务。申请认领和驳回不触发。

评估使用客户当前真实销售负责人（销售、主管或总经理）的有效身份和权限；实际发起变更的销售、FDE 或运营保留为触发人。FDE 没有新增商业写权限。无有效负责人时不假造身份。

同一次触发和事实版本幂等；重复归档不产生重复任务。模型调用前后复查身份、归属、事实、权限契约和公司配置。结果失效时留存过期回执，不写入风险。已经提交业务结果、但队列确认中断的任务通过 `ops.job_effect` 避免重复生成。

新结果使用 `personal_risks` 能力，`surface=customer_risk` 区分客户评估。未启用中台的公司继续原接口；启用中台的公司先尝试中台，超时或结果不合格按原总预算使用原接口。没有新增独立 Agent 绑定，也没有扩大公司灰度。未将空数组自动解释为健康。

## 结果契约

输出仅包含 `outcome`、`reviewed_visit_ids`、`risks`、`reason`。结果必须列明本次全部输入拜访 ID，风险证据必须逐字来自对应拜访的正文或下一步行动；类型、范围、额外字段、重复风险及跨客户来源严格校验。原接口与中台用同一校验函数。

审查覆盖与风险条数分别约束：全部输入拜访均须出现在 `reviewed_visit_ids`，`risks` 最多 8 个独立重点风险，不要求每条拜访各产一条风险。公司业务指引之后附加后端固定自检，明确数量、来源和证据边界，并纳入配置指纹。超限返回仍整体拒绝，不由后端截取后放行；契约失败使用固定错误码，不将被拒绝的原文写入错误消息。

`outcome` 分为 `risk_found`、`no_risk_identified`、`insufficient_evidence`。明确无风险需要非空拜访正文及完整覆盖；截断、无拜访、失败均不能产生健康 100。事实仍有效的无风险回执最多使用 7 天，后续有效业务变更会重新评估；没有安排全库定时模型调用。

`risk_found` 保存为原有待处理风险，客户/商机/负责人均由后端事实确定。已解决或接受的风险不复活；无风险评估不自动解除已有风险。评估判断与人工风险处置职责分开。

## 运维补评与重试

使用服务已有运行环境和普通数据库角色，不在命令中提供密码或 Token。先预览，再明确 `--apply`。命令示例中的标识均为占位符。

```bash
python backend/scripts/customer_risk_assessments.py \
  --workspace COMPANY_EXTERNAL_ID --admin-account ADMIN_ACCOUNT \
  --customer-id CUSTOMER_UUID --request-id REQUEST_UUID

# 核对预览后，同参数增加 --apply 才会排队。
```

同一个 `request-id` 和事实版本重放复用原回执；失败后主动重试使用新的 `request-id`。`--all-authorized` 必须明确指定，默认最多 20 个、上限 100 个。本轮不自动对全库客户批量调用模型。日常任务的基础设施暂时失败沿用队列重试；已明确失败的模型请求不会被后台无限重打。

回执保存覆盖 ID/版本、数量、截断标记、事实/配置指纹、时间、触发人、执行人、状态、结果和推理编号。现有后台审计补充客户风险评估回执关联；不向小程序暴露内部评估数据。

失败推理按同公司、同任务、同执行人、同角色、同能力及本次开始时间补关联；新尝试先清空旧推理编号，历史调用仍通过任务编号追溯。关联沿用当前执行身份的 RLS 和任务租约，关联失败不能把业务失败改为成功，也不能吞掉原异常。
