# 飞书 HTTP 400 错误分类修复

本次准备基于本地 `569d0ac`，分支 `codex/v3-history-active-customers`。范围仅后端传输、定向测试和本记录；不修改数据库、源数据、同步配置、通知设置或队列记录，不在此步骤提交或部署。

## 已确认的代码问题

`FeishuClient.request()` 已经把多维表格的 `1254009`、`1254044`、`1254045` 作为明确拒绝，交给原队列重试。原 `_send()` 在 HTTP 400 时只保留限流和写冲突码，把上述错误提前变成 `HTTP_400`，使已有分类规则失效。

修复让 HTTP 300–499 响应中合法的正整数 `code` 进入同一套既有分类；只保留数字，不提取或记录 `msg`、业务正文、凭据。无数字码、零、负数、布尔、字符串、浮点、数组或对象码仍按普通 HTTP 错误处理。

## 保持的行为

- 字段错误交回原队列，下一次重新读取源记录、远端字段和稳定 ID；传输层不立即重放字段失败的写入。
- `1254607` 转为 `DATA_NOT_READY`，等待至少 10 秒后由队列重试；若服务端等待头更长，采用更长的时间。下一次仍查询相同系统 ID，创建时沿用原稳定幂等键，不为重试换键。
- 未识别的数字错误码保留为 `FEISHU_<数字>`，仍不可重试；不会把所有 HTTP 400 当作临时故障。
- 只有既有的明确 token 失效码可刷新一次 token；最多两次发送，不增加第三次。
- HTTP 429 继续按限流处理；HTTP 5xx、网络超时的读写已知／未知结果策略保持原样。
- 数字错误分类属于内部同步消费契约，公开 API 的请求和响应结构没有变化。

## 与现场失败的证据边界

本次分类缺口已由静态代码和定向测试确认。新诊断 hook 随后实际捕获一次 `create` 返回 HTTP 400、数字码 `1254607`；因此至少这次现场失败可以确定属于数据暂未就绪，不是权限不足或字段缺失。此前四条旧 `HTTP_400` 没有保存数字码，仍不逐条倒推它们的原因。

[飞书新增记录官方说明](https://open.feishu.cn/document/server-docs/docs/bitable-v1/app-table-record/create.md)将 `1254607` 解释为前置操作未完成或计算处理耗时，并建议等待重试。该说明还指出同表版本处理串行，并发请求可能触发此错误。

并发评估：旧表级锁只保护 `guard + create/update`，字段和稳定 ID 查询原本已在锁外；移除它扩大了同表写并发。外部编辑仍可能触发暂未就绪，因此排队重试仍有必要。扩大全局 Worker 数量不能替代同表写入约束；需按实际成功写入速率和写请求耗时评估吞吐。

本次执行决定：不在这项补丁中恢复表级锁；临时批量消费者维持 12 路、按同表 3 次/秒平滑发送，不升至 18 路，重复出现压力错误时停止观察并重新评估。这是临时批量任务的发送上限，不代表飞书保证的吞吐或并发能力。常驻 Worker 仍为单消费者；同表串行、不同表并行等后续批量优化另行验证。本代码补丁只增加错误分类与明确退避，不修改消费者调度或锁。
