## 1. 需求理解

需要公司能够管理“系统按什么标准做判断和展示”，并能查明“某次业务为什么得到这个结果”。管理对象包括 Agent 路由、业务判断标准、准入要求及基础页面行为；个人临时搜索、筛选、排序不属于公司规则。

建议复用现有运营后台，增加两个相互关联的管理区域：

- **Agent 运行审计**：从一次业务操作查到每次请求、完整输出、校验、兜底、最终结果及业务影响。
- **公司规则配置**：公司统一定义规则，版本化发布；后端、中台、原 API 和前端按职责消费相同版本。

这里的“公司”先建议映射现有 workspace。部门个性化规则、编辑与发布角色、历史结果处理方式仍需确认，不默认放开。

## 3. Agent 运行审计怎样做

### 3.1 默认列表：一次业务一行

建议 AI 调用管理增加“业务运行”页签，现有请求明细与用量保留为另两个页签。

业务列表显示：发起时间、业务能力、发起人/当时角色、权限范围、关联对象、最终结果来源、总耗时、业务状态、兜底原因、使用规则版本。支持按 Agent、来源、业务状态、错误类别、时间、人员、对象和测试标识筛选。

默认中文状态可以是：

- 中台结果通过，业务已完成。
- 中台超时，原 API 接续完成。
- 中台输出校验不通过，原 API 接续完成。
- 直接使用原 API（中台关闭、未配置或未命中适用范围）。
- 结果已生成，等待人工确认。
- 两条路径均未给出合格结果，业务失败。
- 推理通过，但保存失败／保存状态待核对。
- 审计回执不完整，状态未知。

“原 API 完成”不能计为“中台完成”；没有经过中台的请求也不能统计成一次兜底。生成商机候选、拜访待确认和正式写入分别呈现。不能将推理失败、人工拒绝、用户取消都归成同一种失败。

业务关联优先使用稳定的 run_id 或业务 job/触发对象关联，每次推理 operation_id 作为子项；operation_id 当前可能随 Worker 尝试变化，不能把它单独当永远不变的业务主键。作战地图还需补齐没有通用 run_id 的统一关联。

### 3.2 详情：完整链路和证据

| 阶段 | 需要看清的内容 |
|---|---|
| 触发与取数 | 哪个业务入口、谁触发、当时角色/范围、事实截止时间、关联记录 ID 与数量、输入字节数及内容哈希 |
| 有效配置 | Agent ID、后端版本、规则/提示词/输出契约版本、中台开关及选路原因、中台等待预算与总预算、原 API 模型 |
| 中台请求 | 是否真正发送、HTTP 状态、首事件/首内容/完整结束时间（有证据才展示）、conversation/message/task ID、完整结果/部分结果/空结果、停止请求及回执 |
| 校验 | JSON 是否可解析、缺失/类型错误字段、ID/枚举/证据引用校验、业务准入决定；低分不准归档属于审核结论，不等同模型接口故障 |
| 原 API 接续 | 触发原因、剩余预算、每次实际请求、返回与校验结果；受控关闭/拦截明确标为测试，不伪装远端故障 |
| 业务结果 | 最终采用哪一路、生成哪个结果/候选、是否等待人工、谁确认、哪些任务/风险/评分实际保存、是否重复、失败或待核对原因 |

前台只看到原有业务交互，提供方与故障细节留在后台。

对运行版本，必须区分“后台期望快照”“中台查询到的已发布快照”和“本次运行证实的快照”。当前 filtered_facts 无实际执行快照证明，应显示“未能核实”，不能凭 CLI 已发布版本填充实际执行版本。模型也区分后端原 API 模型、中台配置模型及中台实际返回模型。

默认详情提供可读的业务输入摘要、最终结果和脱敏错误。查看已有授权范围内的原文/评分证据另走对象权限校验与查看留痕；不把完整客户正文、录音、凭据塞进普通系统日志。为排障保留受控、限期的失败输出结构样本/类型摘要和哈希，避免再次出现只知道 action_plan 不合格、却无法定位形状的问题。审计查看不能绕过现有工作空间和对象权限。

平台日志跳转只能协助定位，不承诺用户具有中台日志权限。建议支持导出脱敏排障包：关联 ID、时间线、预算、输入规模/哈希、事件/校验错误、有效版本和最终业务状态；默认不含业务原文、密钥或签名 URL。

### 3.3 统计口径

分别提供：中台合格输出率、业务完成率、兜底救回率、直接原 API 完成率、超时率、校验拒绝数、待确认数、未知数、耗时 P50/P95。每项能展开分母，显示样本量；不把七个测试样本当长期稳定性。

中台合格输出率以实际发出的中台请求为分母，分子须完整输出且通过契约。兜底救回率以实际触发兜底的业务推理为分母，分子为原 API 校验通过。业务完成率依据该业务自己的终态；待人工确认另列，不能自动算正式完成。未知与仍运行单列，导出统计必须说明是否排除。

测试记录与正式记录需有服务端可信来源标识，不按客户名称包含“演示”猜测。平台一次调用和它内部模型/工具请求是不同计量口径，不混算。现有受控拦截会落一条 provider_attempt 且标记 network_dispatch_suppressed；新“实际网络请求数”必须排除这类未发送记录，业务测试链路仍保留。

实现应沿用现有调用审计、业务 run、job/effect、业务对象与操作日志建立关联，补齐分阶段事件和失败终态，不另造一套可编辑的业务事实。缺失的历史证据显示未知，不补造原文和成功。

## 5. 规则的唯一来源与生效方式

### 5.1 三类配置分开管理

1. **业务政策**：公司可修改的阈值、评分说明、调度默认值及基础展示策略。使用有类型、范围和依赖校验的表单，不让运营编辑任意脚本。
2. **Agent 运行配置**：绑定、模型、超时、试点范围、版本引用、可用性；只向对应管理权限开放，密钥仅引用或安全录入，不回显原值。
3. **代码与安全约束**：工作空间/对象权限、ID/枚举合法性、幂等、事务、人工确认边界、金额精度及协议结构。保留代码校验，不作为普通“关闭校验”开关。

现有字典、表单、rule_set、能力框架、AI配置版本优先复用；建立统一的“规则目录+发布版本”，由每类规则的执行器明确消费。不能只弄一个任意JSON库而继续让旧常量执行。

### 5.2 中台、原 API 与后端不能各改各的

当前原 API 走 AgentPromptBuilder/本地覆盖，中台输入只含 mode/role/user_text/current_time/facts，中台提示词另在平台维护。**当前修改本地prompt_overrides并不等于同步修改中台 Agent。** 部分模式用覆盖提示词替换基础提示词，另一些追加固定契约，管理界面应能查看最终有效提示词及来源。

建议公司规则是唯一业务来源：

- 确定性规则直接由后端执行，前端读取同版本的显示投影。
- AI 评分细则转为版本化政策内容，原 API 和中台均使用该政策；不把客户正文中的要求当政策。
- 与中台验证可支持的消费方式：每次输入传后端可信政策，或由发布步骤把政策同步成中台新版本；不假设现有 Agent 已支持动态政策。
- 平台固定提示词保留角色/能力和契约；业务细则与公司政策不可重复独立编辑。中台人员调优作为草稿，再经相同样例验证和版本关联。
- 业务版本只有在后端、兜底、必要前端及中台消费确认一致后，才显示“已生效”；不兼容的 Agent 保持上一验证版本或原 API，不能静默混用新旧标准。

平台运行版本当前无法证明，发布流程只能显示“配置核对+消费验证”的证据层级。严格运行锁版本属于平台需补能力，不能用本地 expected_snapshot 假装保证。

### 5.3 发布、历史与回退

建议草稿 → 看差异/样例试算 → 发布新版本 → 生效核对 → 可回退。每次记录修改人、原因、影响范围、生效时间、规则版本与关联中台版本；带乐观版本检查防止多人覆盖。回退发布一个引用旧内容的新版本，保留全过程，不改写历史发布。

发布前应能看到影响，例如：潜力阈值70改75，哪些已知样例的分类会变；拜访门槛60改70，哪些样例会不再通过。AI样例复测与纯规则试算分开，费用和执行事实明确，不自动写生产业务数据。

建议默认新版本用于新发起的审核/分析。既有评分、已归档拜访、已生成任务不静默重写；需要重算时以独立批次、影响预览与业务授权处理。处于等待人工确认的结果显示审核时版本；是否允许旧版结果继续确认是业务决策，建议保留明确有效期，过期再要求重审。

四象限“当前投影”如要按新阈值立即重分类，也应保留旧评分/旧分类/旧规则，并展示重分类来源，不能只在前端换色造成前后端历史矛盾。

基础展示配置在页面进入/明确刷新时载入，当前滚动过程固定版本，避免消息突然换序。后端分页、插入位置与前端锚点需一起支持；旧客户端使用已验证默认值。基础顺序发布不应顺带打开问数入口。

future_due 当前也被风险草稿使用。实施待办规则时须明确区分“待办执行时间”和“风险建议处理时间”，不能修改一个共享函数就隐式改动另一类业务。

## 6. 建议实施顺序及验收

1. **先补真实审计闭环**：重点补齐超时→原 API→业务校验→最终状态，以及双失败的终态记录。先用单个现有 Agent 验证，再推广公共逻辑。已有超时和经营总结原API格式问题仍需修复，审计完善不能替代稳定性修复。
2. **建立公司规则发布基础并接四象限**：从现有70/70等价迁移开始；验证前后端分类、阈值边界、版本记录和回退。
3. **接拜访准入整组规则**：先保持>60等现有行为；覆盖60/61边界、首访、下一步、原文修改后重审、中台/原 API 同政策、并发规则发布及人工归档。
4. **接基础展示和待办时间**：首页desc保持；显式切换测试插入/分页/滚动/恢复；待办覆盖北京时区、跨日、缺日期、过期、原管理任务截止时间不变。
5. **按业务确认逐项扩展**：客户层级、商机等级/阶段、风险健康阈值、指标目录、能力框架。继续“接一项、测一项”，每项验收包括改配置后实际消费者生效，不能只验证配置保存成功。

权限验收须覆盖当前运营/系统管理员边界、跨workspace禁止读取/修改；日志导出脱敏；测试故障不遗留生产。AI审核低分、候选待确认、正式写入成功分别验证，不以HTTP200替代。

## 7. 建议与用户对齐的三项决策

1. 公司业务规则首期是否统一一套、部门例外后续再做？建议是；用户个人筛选偏好仍独立。
2. 谁可修改和发布？建议运营可维护业务规则，系统管理员发布；Agent凭据和路由等技术配置仅系统管理员。若团队暂时只有一位管理员，可由同一人承担，不强加多人审批。
3. 首批范围是否采用“Agent审计+四象限+拜访准入+首页基础顺序+待办默认时间”，其余建立目录后逐项做？建议采用；保留当前值、新分析用新版本、历史不自动重算。

用户已授权按上述首批范围实施：公司统一工作空间政策、运营维护业务草稿/管理员发布、管理员维护技术配置；其余候选仍待逐项业务确认。
