# 企业业务身份与伙伴档案关联

本增量对应 `IDENTITY-DRAFT-20261013-BE01`。中央版本、运行环境和发布状态仍以主仓 `docs/PROJECT_FACTS.md` 为准；本文件仅记录接口及实现变更。

## 行为与兼容

- `crm.customer.id` 继续作为企业稳定 ID。`business_identities` 支持客户、伙伴、双身份；来源“合作伙伴”与业务身份相互独立。
- 新建省略身份默认客户；更新省略身份保留原值。客户身份新建或从纯伙伴添加客户时，客户类型必须为潜在客户、商机客户或已成单客户。现有客户可保留未改变的历史类型，包括只添加伙伴身份时；移除客户身份清空类型。
- `partner_profile_id` 是本企业自身稳定伙伴档案。一旦关联不可替换或清空；移除伙伴身份保留关联，不停用全局伙伴档案。同名历史伙伴需要明确选择 ID，不自动合并。
- 请求 `partner_id` 对应读回 `primary_partner_id`，表示关联外部伙伴；名称仅为快照。禁止跨公司、无效新关联、自关联。旧纯文本不猜测 ID。
- 普通销售仍走申请、审批、待认领、认领。审批事务原子写入企业、自身伙伴档案、联系人和审批结果；不授予 `partner.manage`。
- 运营后台审批表单只读展示并透传原申请的业务身份、自身伙伴档案 ID 和所属伙伴档案 ID；纯伙伴不显示客户类型控件，提交类型为 null。客户名称、部门、联系人等原审定字段仍可修正；已关联的所属伙伴名称随固定 ID 保留，历史纯文本仍可编辑。原版本锁、权限、事务与接口契约保持不变。
- 旧审批客户端省略新增身份或伙伴 ID 时，由后端在锁定申请后保留原值；旧表单为纯伙伴带来的客户类型置空。显式身份/ID 仍按创建契约验证，显式 null ID 与省略在幂等摘要中区分。此修复不新增迁移、不改变 OpenAPI 结构。
- 原有客户端省略新增字段时，幂等请求摘要保持兼容。旧商机绑定不会因企业后来变为纯伙伴而阻断无关更新；新建商机必须选有客户身份的企业。

## 目录和分析

- `/customers`、`/customers/claim-pool`、`/console/customers` 接受 `business_identity=all|customer|partner`，缺省为 all。目录及管理分页在计数、分页前过滤；空页仍返回正确总数。
- claim-pool 的 `can_read_customer` 由原有 `customer.read` 授权计算，仅供按钮展示；详情接口和 RLS 仍独立鉴权。目录可见不等于详情可读。
- `/customers/portfolio`、`/customer-assets/map` 始终以客户身份为基础集合；选择 partner 时只包括双身份。
- 纯伙伴不进入客户计数、画像和评分，详情六维评分为 null、状态为 `not_applicable`。新评分任务不入队，已排队任务再次校验；客户问数/新商机 Agent 入口拒绝纯伙伴。没有新增伙伴 Agent。
- 管理台企业总览沿用企业范围；历史财务事实不按当前身份重写。

## V239 与验证

- 新增身份、自身伙伴和关联伙伴字段及约束。创建事务标记 `identity_created_xid` 不可更新；旧行为空，授权判断用 `COALESCE(...,false)` 明确拒绝 NULL。
- 所有旧 202 条迁移 checksum 内容不变，V239 后为 203。最终 V239 删除按客户表读取权推断角色的广泛授权 wrapper；精确 `runtime_permissions.json` 仅更新 V239/203 指纹及 API 三个新函数签名，Worker、飞书、平台角色、表/列/序列/RLS 权限均保留。权限由原安装与升级授权流程下发，函数内部仍校验业务权限。
- 最终隔离 PG16：37 项通过，合成库迁移登记 200→201，全部旧 checksum 行值保留，重放为 unchanged。覆盖三类审批、幂等、同名显式绑定、跨公司/无效/自身关联拒绝、空页计数、创建权限旧行拒绝、完整失败回滚、并发单绑定及原 RLS。测试实例 finally 停止成功。
- 最终 155 项定向测试及 OpenAPI 检查通过；本增量修改的 Python 文件 F 检查通过。全局风险路由 `risks.decide_risk` 漏登记、旧 197 条迁移硬编码测试以及两份旧报表测试的 F 检查问题已在 f734 基准存在，独立记录，不声称全库检查全部通过。
- PG03 的业务合成角色预置较宽权限，不能证明最小 grant。PG04 专门使用原 `runtime_roles.provision_new`、原 `upgrade_permissions.reconcile` 和原 `verify`，验证 V238→V239 的精确四服务角色权限；API 三函数实际建档/目录调用成功，Worker 可读身份但无新 helper 权限。尾段独立记录 Worker/飞书/平台共九次目标 SELECT 的 42501 拒绝，PUBLIC 及旧飞书组也无新函数 EXECUTE。原 PG04 最后粗粒度负例被保留，由尾段证据替代；实例已停止。此为隔离服务角色验证，不是共享 LOCAL/生产运行验收。
- 隔离测试没有访问共享 LOCAL、生产或调用模型。后续真实 LOCAL 要再次核对同一库 OID、实际迁移账本和受限角色，再做前端/API 验收。此文件不构成发布回执。

## 配套与恢复

新后端要求 V239，旧 V238 后端不列为恢复目标。需要恢复 Web 时保留 V239 与兼容新后端，或按明确方案向前修复。生产登记数与 LOCAL/合成库不同，不能相互套用。跟进草稿由 Web/小程序本地持久化实现，本增量未新增后端草稿 API。

生产工具后继使用 `enterprise_identity_1.2.1` 固定范围：仅接受 V238/202 checksum/233 登记到 V239/203/234，固定唯一 V239 SQL 和精确 API 三函数权限清单。原备份、停写、三进程、配置、客户端兼容、完整账本、源码闭包及失败后维护门槛保留；迁移尝试后不自动退旧后端。新 V239 与既有 1.2.1 发布守卫共 126 项离线测试通过。旧 `test_release120_production_acl.py` 的两条登记夹具已在 f734 被完整登记守卫拒绝，19 个旧测试未进入其预期断言；另有基准复现回执，不将其算为本次通过。工具的离线通过不等于真实部署窗口获准或生产切换成功。
