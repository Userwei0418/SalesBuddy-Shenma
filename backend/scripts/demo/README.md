# 真实 FDE 演示数据录入

当前工具为 `fde_demo.py`，固定故事在 `fde_scenarios.json`。它不会随服务器或小程序启动运行，必须由交付负责人显式执行。素材描述为虚构，客户、认领审批、商机、拜访、任务及通知必须通过正式 HTTPS 业务接口落入获准使用的演示数据库；脚本存在或离线测试通过不等于已经录入。

旧 `seed_visit_demo.py` 保留为历史实现，使用免密登录、旧客户建档和 70 分口径，**不得用于当前环境**。本工具从现有账号密码登录，采用运营建档、销售申请认领、运营审批；拜访正文为沟通内容与下一步计划，归档必须真实分数 **>60** 且下一步审核通过。

## 场景与账号

四个标有“【演示】”的虚构客户：澄星制造、云帆物流、望岚软件、启明服务；下设六条带可读名字的商机。客户公司建档编号明确以 `DEMO-` 开头。使用 OPSADMIN、XS001、XS002、XS003、FDE001、FDE002、FDE003、FDEL001，不创建新账号，不改现有角色、密码或公司规则。

| case | 场景 | 计划归档 |
| --- | --- | --- |
| `01_first_visit` | 新客户，销售选择周玮、张家涛，两人分别录入 | FDE 2条、销售1条 |
| `02_continuous` | 同商机连续跟进，分别累计本人次数 | FDE 2条 |
| `03_parallel_project` | 同客户另一个商机，仅关联叶源 | FDE 1条、销售1条 |
| `04_existing_customer` | 老客户持续跟进，销售与两位 FDE 分别记录 | FDE 2条、销售1条 |
| `05_lead_participation` | 李鹏程亲自参与，与周玮分别记录 | FDE 2条 |
| `06_shared_review` | 客服政策版本检索，成员与负责人分工 | FDE 2条 |
| `07_quality_revision` | 一条低质量候选只保留草稿，再录完整材料 | FDE 2条，另1条不归档候选 |
| `08_handover` | 协助名单加入／移出、资格回收、任务转交、岗位领取、拒绝及待接收 | 4个任务，不产生拜访 |

总计 **13条 FDE 本人归档、3条销售拜访、1条低质量候选**。是否真的可归档取决于模型实际结果，脚本不会改分数或伪造通过。销售所选协助名单不代计 FDE 拜访次数。

日期在新状态文件的 `base_date` 锁定，拜访覆盖此前6天至当天；下一步截止时间和预计关单日期相对基准日期展开。季度计划记录真实预测值，预测不当作确收／回款实绩。首次拜访材料包含主营业务、需求、预算和联系人角色。

## 分步执行

使用后端 Python 环境。macOS/Linux 中 `getpass` 隐藏输入；非交互运行只能通过 stdin 在内存中传递。密码不得放命令参数、环境变量、状态文件或仓库。每次命令结束退出自己建立的临时会话，不改小程序当前登录。

下列命令中的状态路径必须在仓库外；同批次持续使用同一个文件，不删除后重新创建，不用新状态盲目接管同名客户／商机。新状态遇到同名但没有本批回执会停止，等待人工核对。

```sh
backend/.venv/bin/python backend/scripts/demo/fde_demo.py \
  --state /absolute/evidence/fde-demo-state.json \
  --phase prepare --case 01_first_visit
```

1. **prepare**：运营创建客户，销售申请认领，运营通过，销售创建对应商机和协助名单。每个 case 自动准备自己的依赖；`08_handover` 还执行已授权的演示任务和名单调整。可以省略 `--case` 顺序准备全部案例。无模型调用，但正常业务变更触发的后台分析任务不会被压制。
2. **review**：使用同一参数将 phase 改为 `review`，逐条创建关联客户／商机的会话并调用真实 AI，候选保存在 `visits.<记录编号>.candidate`。建议先用 `--record v01` 跑一条，核对后再继续；`--record` 会确定所属 case。模型仍处理中时停止观察，原参数重跑继续查询原 run，不重复发送消息。
3. **核对候选**：交付负责人必须实际阅读状态文件中的 `original_text`、`candidate.fields`、`quality_review`、关联客户／商机、日期和首次拜访信息，确认没有捏造事实，再为该条填写 `checked`。脚本不会自行标记审核通过。
4. **archive**：只对候选已核对的指定记录运行 `--phase archive --record v01`。后端接收真实审核 run，归档后核对创建人与记录人、商机关联、正文、分数、本人次数及两类回执：录入人通过 `/assistant/home.archived_visits` 收到本人成功卡；被选中的 FDE 通过 `/notifications` 各收到一条协同归档通知。FDE 本人录入时后端自动将本人记为参与者；销售本人不要求收到 FDE 协同通知。未审核、候选变化、分数不够或下一步不通过都会停止。已有成功回执的记录跳过；不重复入库。
5. **verify**：`--phase verify --case 01_first_visit` 回读已归档条目、本人历史、本人总览成功卡、参与者通知和负责人团队看板。全部录完后省略 case 验证完整批次。`final_dashboards`、`final_personal_history`、各记录 `readback`、`archive_overview_receipt`、`archive_notifications_by_account` 和任务回执用于编写最终演示手册。

核对后，`checked` 的结构如下，四个值必须对应实际核对的候选：

```json
{
  "candidate_hash": "从该记录 candidate_hash 复制",
  "run_id": "从该记录 run_id 复制",
  "reviewer": "实际核对人或执行核对的代理说明",
  "reviewed_at": "实际核对时间，ISO 8601"
}
```

`v12_low` 必须保持不归档。若它意外被模型评为可归档，脚本会停下并记录观察结果，应将其作为模型评分问题反馈；不能为了演示强改分数。完善后的独立记录为 `v12`，与低质量候选保留各自原文和审核证据。

## 中断与重放边界

每次写操作前将幂等键、账号、路径和精确请求正文原子保存。发生网络失败时立即停止后续写入；相同状态重跑复用原键和正文，版本号也不重新替换。成功操作直接使用本批回执。状态文件有独占锁，同批不并发执行两个命令。

旧服务器的 `POST /conversations` 没有请求级幂等，未知结果不能盲目重放。**仅在主线已经部署并验证原生会话幂等后**，执行命令可以追加 `--conversation-idempotency-verified`。此参数允许恢复未知会话结果，不绕过任何客户／商机资格或内容审核；未确认服务器能力时默认停止该重放。

API 错误只记录安全状态码与预设错误代码，不输出响应正文、密码或令牌。某一步失败后，已创建的演示记录和回执保留，下一步必须从同一状态恢复；不执行清库、批量删除或临时关闭业务通知。

离线检查：`backend/.venv/bin/python -m pytest backend/tests/test_fde_demo_runner.py -q`。这些测试使用独立传输夹具验证工具的恢复和审核边界，不是线上成功证据，也不替代小程序实际展示验收。

## 根据实际核对结果修正候选

使用 `revise` 阶段，修正清单放在仓库外，每次明确指定一条 `--record`。它不会直接归档，也不允许修改评分、审核结论、关联客户/商机或低分专用案例 `v12_low`。已经发出归档请求的记录不允许从此入口再改。

```json
{
  "schema_version": 1,
  "revisions": [
    {
      "record": "s02",
      "source_candidate_hash": "原候选当前的candidate_hash",
      "fields": {"follow_up_record": "实际逐字核对后填写的完整沟通正文"},
      "reason": "说明原文依据和为什么需要修改，不填任何新商业事实"
    }
  ]
}
```

```sh
backend/.venv/bin/python backend/scripts/demo/fde_demo.py \
  --state /absolute/evidence/fde-demo-state.json \
  --phase revise --record s02 \
  --revision-file /absolute/evidence/fde-demo-revisions.json \
  --conversation-idempotency-verified
```

脚本复用后端 `domain.visit_review.review_text`，与小程序 `visitFlow.reviewText` 使用同一“拜访审核 v2”语义：

- 沟通正文、下一步或首次拜访画像发生变化：以修正后的完整值发起正常会话与消息，通过真实 AI 重新审核。评分只使用服务端新回执；重审后的辅助提取不能覆盖已核对字段。新分数未通过时也如实保留，不沿用旧分数。
- 非首次拜访的可选画像、其他不影响 `review_text` 的辅助字段变化：复用原审核 run 和原质量结论，只修改人工字段，不重复调用模型。这样与前端“仅正文或首访画像变化才重审”的规则一致。
- 两种情况都会清空 `checked`，交付负责人必须再次核对当前候选、新 `candidate_hash` 与实际 `run_id`，然后才能进入独立的 `archive` 阶段。修正进行中禁止归档。

每次修正保存在 `visits.<record>.revisions`：原候选、原 run、原 hash、原核对信息、修正清单、提交字段、是否需重审、实际重审返回及最终候选 hash 均留存。`original_text` 始终不改，低分样例也不改。此记录明确区分模型原始输出与人工修正后的候选，不把修正内容伪装为模型首轮输出。

网络中断后使用同一修正清单和参数恢复，沿用已保存的 conversation/message 幂等回执，不重复新建付费请求。若服务端明确失败，原修正保持失败，不因再次执行相同命令自动重试。确需再次调用时，发布负责人重新核对并用新的修正说明提交清单，脚本记录 `retry_of_revision_id` 关联原失败；原始失败证据不删除。候选 hash 变化或另一个修正仍运行时拒绝覆盖。

本轮最小修正例：`v05` 清空未提供的主营业务、联系人角色和预算，`v10` 清空把报价态度误当成预算的字段；两条都是持续跟进，可复用原审核。`s02` 恢复原文明示的销售刘志德与协助 FDE 叶源共同跟进，需要对正文重新审核。候选中的客户类型、系统创建日期应由正式保存流程回读系统数据，不为这些服务端字段逐条重复调用模型。
