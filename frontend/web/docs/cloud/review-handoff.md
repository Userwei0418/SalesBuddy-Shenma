# SalesBuddy：交互方案共评与交接

2026-09-20｜共同起点：Web 0.6.12／小程序业务基线 1.0.6

**目标：大家基于同一份代码和业务规则出方案，按具体改进点选择保留，最后由一个集成人合入并验收。**

状态说明：现有业务约束和 Web V1 设计规则沿用已确认要求；下述团队分工、评审步骤和方案选取办法是本次建议，实际负责人由团队填写。文档交付不代表团队已经采用，也不代表所有页面已符合规范。

## 1. 先对齐三件事

| 对齐项 | 共同依据 | 不要混淆 |
|---|---|---|
| 做哪一版 | Web 0.6.12；小程序 1.0.6，源码基线 6b8aa7a | 从别的旧包出方案，须先列差异 |
| 改什么 | 每个方案只写清一个主要问题、角色与使用场景 | 本轮已修复项不自动算仍存在的缺陷 |
| 怎么判断好 | 同样数据、身份、窗口、入口与操作目标 | 看起来更漂亮，不等于操作更好或业务正确 |

现有规范使用 [Web 设计规范 V1](design-standard.md) 和 [验收清单](checklist.md)。保留 P／V／C／T／B／G 规则编号，方案直接引用；不另起一套相互冲突的颜色、组件和术语。旧规范出现“首页工作台”的地方，页面命名统一按本项目已确认的“总览”使用。

## 2. 设计可以调整什么

**可调整：** 信息层级、布局分栏、列表密度、留白、筛选位置、输入方式、展开方式、操作反馈、键盘和窄屏适配。

**业务变更要单列：** 接口字段、必填条件、数据口径、对象关联、权限、审批、任务状态、AI 处理与归档顺序。不能混在视觉优化里直接改变。

| 典型场景 | 必须保持的含义 |
|---|---|
| 客户认领 | 提交申请后等待运营审批，不代表已获得客户归属 |
| 任务完成 | 通常提交说明后由发起人确认或驳回；自建自领沿用直接完成规则 |
| 拜访 | 核对内容、质检、人工确认、归档；改内容后按原规则重新质检 |
| 待办推荐 | 下一步行动是记录；采纳建议还须确认任务，不能自动视为已建待办 |
| 商机与客户 | 关联、编辑和协助名单维护遵守后端能力；不靠角色名称猜权限 |
| 经营指标 | ACV、确收、回款分别展示；缺失不显示成 0 |

Web 与小程序可以有不同布局，但同一对象、角色和动作的业务结果应一致。新增业务建议填写 [规则变更单](templates/02-规则变更单.md)，明确需同步的小程序、后端和 Agent 部分；普通布局调整无需另走业务确认。

## 3. 每个人怎么出方案

先复制 [任务单](templates/01-任务单.md)。方案编号建议使用 `UX-页面-作者-A-v01`；同一问题最多先比较两个候选，避免一次全站重画。

每份方案交回以下六项：

1. **问题与目标：** 谁在什么步骤遇到什么问题，改善后应有什么变化。
2. **前后对比：** 同一窗口、数据和角色的当前页面与候选页面；注明版本。
3. **完整交互：** 可点击原型或运行入口，说明进入、操作、返回及恢复；只有截图要标“仅视觉稿”。
4. **状态与规则：** 正常、加载、空、错误、无权限；涉及表单再补校验、提交中、失败恢复。引用规则编号和复用组件。
5. **影响范围：** 修改哪些页面／组件／文件；业务、接口和权限是否变化，若有就另列。
6. **验证与限制：** 测了什么、没测什么、存在什么问题；原型、前端本地、真实 API、跨端读回分别填写。

有仓库时按方案开独立分支；当前 Git 远程仓库为 shandianT/raccoon-salesbuddy-web。没有仓库就各自解压到独立目录，不多人覆盖同一份文件。代码结果交回差异补丁，或附明确改动文件清单的完整包；不要只交 `dist`。

## 4. 怎么选哪些留下来

**按改进点选择，不必整套 A 或整套 B。** 例如保留 A 的客户图表联动、B 的表单分组；组合后仍须再检查密度、组件、状态和操作位置是否统一。

先通过业务与交互底线：权限和数据正确，关键流程可完成，失败可恢复，长内容不遮挡操作。未通过的方案先修正，不用视觉评分抵消问题。

再用同一批操作比较下面四项，记录证据和取舍，不预设“每个页面都要两栏／三栏”：

| 比什么 | 怎么看 |
|---|---|
| 更好找 | 首屏能否找到对象、重点状态和主要操作；必要信息是否被隐藏 |
| 更省步骤 | 完成同一任务的点击、跳转、滚动、反复返回是否减少 |
| 更清楚 | 分区、筛选范围、状态、缺失值和反馈是否容易理解 |
| 更统一、易维护 | 能否复用已有组件；是否增加例外、重复样式和实现成本 |

记录到 [方案对比与采纳表](review-decisions.csv)。每个改进点填“采纳／修改后再评／不采纳／待验证”、理由、负责人和证据；“采纳”与“已实现、已验收”是三件事。

**建议首轮只做三个样板：** 总览、客户图表与列表、创建任务。先把首页、业务列表和表单三类模式选稳，再用于商机、认领、详情与拜访；拜访待办推荐另外检查完整确认流程。

## 5. 分工与交接

| 建议角色 | 做什么 | 交回什么 |
|---|---|---|
| 产品／业务负责人 | 确认问题、业务约束和取舍 | 问题范围、业务变更结论、采纳记录 |
| 方案设计者 | 出候选方案与异常状态 | 原型、前后对比、规则与差异说明 |
| Web 集成人（建议一人） | 选择已采纳改进，处理共同组件与冲突 | 改动清单、可运行版本、规范差异 |
| 小程序／后端／Agent 对接人 | 处理被明确标出的业务与契约变化 | 影响结论、对应版本、待解决项 |
| 验收人 | 用相同案例复验，确认没破坏原流程 | 验收单、截图、测试结果与未验证项 |

实际负责人、时间由团队填写，不以本表擅自指派任何人。建议一张共用表维护状态，文件名用明确版本，停止传播多个“最终版”。

## 6. 验收后才成为新版

使用 [页面验收单](templates/03-页面验收单.md)，在 1366×768、1440×900、1024×600 与窄屏检查。重点是首屏能开始主要工作、长内容可查看、关键操作不被遮挡；不要求把所有历史记录硬塞进一屏，也不通过统一缩小字体来掩盖布局问题。

共用案例至少包含：总览下钻任务后仍可切换状态；客户图表和列表数量一致；认领仍需审批；任务确认／驳回／重提；表单校验失败保留输入；拜访归档与建议采纳区分；无权限、超时、空数据可理解可恢复。使用同一份合成数据和角色范围，真实写入另在授权的联调环境验收。

每个采纳项走完：**记录采纳 → 集成代码 → 页面与原流程回归 → 更新规范／示例／偏差 → 生成新包与版本 → 接手人确认启动和使用。** 规则未变时记录“不需更新规则”，不要无意义改版本；规范变化时同步它的示例与检查项。

0.6.12 已有 41 项隔离浏览器检查、1 项构建检查以及解压重建一致性证据；这些是该版局部范围的既有结果，本仓库上传另做构建与单元检查，以实际CI为准。真实认证、Agent 运行、后端写入和跨端读回仍需专项验证。参考包里的历史报告保留各自日期，不累计为本轮成绩。
