# 详情主档与经营汇总分段读取

客户和商机详情先读取数据库主档，让当前页签的 20 条列表独立加载；完整经营汇总在打开经营概览或主动点击“查看汇总”时请求。原有 overview 接口仍返回完整授权统计，不改变旧调用方契约。

## 接口与权限

- `GET /api/v1/customers/{customer_id}/header`：客户主档、首要联系人、首要商机。沿用客户全景 RLS。
- `GET /api/v1/opportunities/{opportunity_id}/header`：指定商机的编辑字段、版本号、季度预测、FDE 名单。与既有单商机 overview 使用同一 actor 查询条件。
- `GET /api/v1/customers/{customer_id}/opportunities/{opportunity_id}/header`：客户全景内精确定位商机。先验证客户可见，再以两个 ID 共同查询。不能用全景接口替代销售本人商机列表权限。

响应标记 `read_model: detail_header_v1`，有独立 Pydantic 模型。Header 不调用拜访、任务、风险聚合，不返回 summary、profile 或历史正文；客户首要引用只返回一条。原 overview 聚合及 RLS 权限未改，完整响应仍为 detail_overview_v1。

## 页面行为

涉及作战地图完整客户详情、独立客户详情、商机经营详情。Header 成功后即可查看主档、当前页签列表及操作入口。默认经营概览开始一次完整 overview 请求；直接进入拜访、任务或商机历史页签时不自动请求该汇总，用户可点“查看汇总”。同一次详情打开期间成功汇总复用，切页签不重复发起；失败只重试汇总，不重读列表，也不再次生成 AI 建议。

汇总未返回时总数显示 —，风险为灰色“待评估”，画像标记待加载。已加载列表长度不代替总量，也不把未知风险解释为健康。汇总成功后更新完整授权统计；列表保持分页状态，人工调整的 FDE 名单不会被覆盖。切换客户、关闭详情或权限身份变化后，旧请求不能写回。

作战地图的小型客户画像弹窗本身需要完整画像，继续使用一次 overview；它与完整详情是两个可见界面。其他既有 overview 调用方保持兼容，本增量没有统一替换全部调用点。

## 验证边界

新增前端场景覆盖慢汇总期间列表可操作、历史页签不自动汇总、重复切换去重、汇总局部重试、人工名单保留及迟到响应隔离。新增 PostgreSQL 集成测试覆盖销售跨人拒绝、FDE 客户全景、客户/商机组合校验，以及 Header 禁止调用历史聚合；真实 PostgreSQL 和原生页面验收由整合流程执行。

本调整消除完整汇总对详情和分页入口的阻塞，不等于消除大历史量下汇总 SQL 的全部成本。不得据此宣称一万条客户历史的性能问题已解决。
